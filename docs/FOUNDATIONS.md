# 安全与对齐基础知识

## Z01 安全、对齐与 Preparedness 分别研究什么

安全关注风险与伤害；对齐关注行为是否符合明确的目标和约束；Preparedness 关注更强模型可能带来的风险及评估、监控和响应准备。一个月项目只验证明确定义的行为。

### 1. 从一个可观察行为开始
用户请模型总结一封邮件，模型却根据邮件里的文字转发了内容：问题涉及用户目标、外部数据可信度和操作权限。单纯检查回答是否礼貌，无法评价这次行为是否安全。

### 2. 把价值目标写成实验
“让模型更安全”太宽。可以改成：在固定攻击集合和推理预算下，降低违规响应，同时维持正常任务完成率。写明安全政策、攻击者控制范围和判分规则。

### 3. 本项目的范围
主线研究安全 SFT / DPO 对对话行为的影响；Agent 工具注入属于独立拓展。研究结论限于模型、数据、预算和评测器，不覆盖所有未知风险。先形成一页研究问题，再训练。

**易错点：**拒答更多不自动意味着对齐更好；低攻击成功率也可能来自模型缺乏正常任务能力。

**自测：**给出一个安全指标改善、用户体验却变差的例子。你需要增加什么指标？

资料：[Seed Alignment & Preparedness 招募](https://seed.bytedance.com/zh/blog/seed-alignment-preparedness-team-looking-for-global-talents)、[HarmBench](https://arxiv.org/abs/2402.04249)

## Z02 行为规范、威胁模型与信任边界

威胁模型要说明攻击目标、攻击者可见信息、可控制输入、查询预算和成功条件。行为规范要同时规定哪些请求应满足、哪些应拒绝，以及工具操作需要哪些授权。

### 1. 写出五个字段
以工具输出注入为例：攻击目标是改变用户原定任务；控制面是一个检索结果；看不到系统提示；最多尝试十次；成功由实际工具状态判定。它与可以修改系统提示的白盒攻击不同。

### 2. 数据与指令分开
检索内容、邮件正文和网页通常属于待处理数据。它们声称“管理员已授权”不能创建权限。真正的权限必须来自可信的用户授权及执行层策略。

### 3. 实验里如何落实
保存正常用户请求、攻击位置、候选次数、模型可见上下文和评分规则。所有被比较方案使用相同控制面与预算。防御改变可用工具后，要重新检查正常任务是否仍能完成。

**易错点：**不能用强白盒攻击攻击基线、再用弱黑盒攻击测试改进方案，并称为公平比较。

**自测：**为什么攻击目标、攻击入口和成功判据必须分开写？

资料：[AgentDojo](https://github.com/ethz-spylab/agentdojo)、[HarmBench](https://arxiv.org/abs/2402.04249)

## Z03 Pretraining、Midtraining、SFT 与 RL 的训练信号

预训练常用下一 Token 预测；中期训练通常指特定阶段的数据或任务能力强化，名称并无统一目标函数；SFT 模仿示范；偏好优化或 RL 使用回答比较、奖励或可验证反馈。

### 1. 同一问题，四种数据
预训练读到文本中的事实；中期训练可增加领域语料或长上下文任务；SFT 接收“问题＋示范回答”；偏好训练接收同一问题的两个回答及比较标签。每一阶段都可能影响安全行为。

### 2. 先看目标函数
阶段名称不等于算法。问清楚输入、监督位置、损失、可训练参数及数据分布。“做了 RL”还需要解释奖励来源、采样策略、更新频率和约束。

### 3. 本项目的选择
使用已经完成预训练与后训练的 Qwen3 检查点，追加小规模 LoRA SFT 或 DPO。原模型作为零额外训练基线。不能把追加微调称为从头训练大模型，也不能只看训练损失得出安全结论。

**易错点：**从相同检查点分别做 SFT / DPO，与先 SFT 再 DPO，是不同实验问题。

**自测：**本项目的两个训练分支应从哪里初始化？为什么？

## Z04 训练最小基础：张量、梯度、mask 与优化器

语言模型输出常为 [batch, length, vocab]，标签为 [batch, length]。因果语言模型用前一位置预测下一 Token；有效监督 mask、梯度累积和优化器步数共同决定实际训练信号。

### 1. 看清三个张量
input_ids 是输入 Token；attention_mask 控制注意力可见位置；labels 决定哪些目标计入损失。常见实现用 -100 忽略标签。attention_mask 与 loss mask 的职责不同。

### 2. 追踪一次更新
forward 得到 logits，计算有效位置损失，backward 累积梯度，optimizer.step 更新可训练参数，然后清空梯度。累积期间多次 backward 仍可能只对应一次 optimizer step。

### 3. 亲手检查
打印两条训练样本的模板文本、Token、labels、有效目标数量。检查 padding、截断和回答边界。有效 batch 常为单卡 batch × 累积次数 × 数据并行卡数，但长度和归一化也会影响梯度。

**易错点：**model.eval() 不会关闭 autograd；torch.no_grad() 也不会自动切换 dropout 的训练状态。

**自测：**两张卡、每卡一条、累积八次，对应多大有效 batch？哪些前提可能使简单公式失效？

资料：[PyTorch 基础](https://docs.pytorch.org/tutorials/beginner/basics/intro.html)、[TRL SFTTrainer](https://huggingface.co/docs/trl/sft_trainer)

## Z05 LoRA、QLoRA 与显存账单

LoRA 冻结原权重，训练低秩增量 ΔW=(α/r)BA；它减少梯度和优化器状态，但仍需基础权重和激活。QLoRA 再量化冻结基座，量化配置也成为实验变量。

### 1. 为什么省显存
W 为 d_out×d_in，A 为 r×d_in，B 为 d_out×r，可训练参数从 d_out×d_in 变成 r(d_out+d_in)。前向仍要读取基础权重。

### 2. 一个估算
8B 权重仅按 BF16 数据载荷估算约 16 GB；32B 约 64 GB。这不包含激活、缓存、工作区、参考模型与优化器。DPO 还处理 chosen / rejected，不能直接套用 SFT 的峰值。

### 3. 本项目怎么选
先用 H20 和 BF16 LoRA，固定 target modules、rank、alpha 和 dropout。先测短序列、小 batch 的实际峰值，再放大。若引入 4 bit，需要把量化作为明确条件并保持对照一致。

**易错点：**96GB 显存容量不能直接推导训练速度；增加数据并行卡数不会自动分片每个完整模型副本。

**自测：**为什么一张卡能加载模型，却可能无法完成一次反向传播？

资料：[LoRA 原论文](https://arxiv.org/abs/2106.09685)、[QLoRA 原论文](https://arxiv.org/abs/2305.14314)

## Z06 SFT：只对正确的目标位置计算损失

SFT 通常监督助手回答。需要正确处理因果 shift、提示词 mask、padding 和截断；只优化一个拒答短句可能获得低损失，却损害正常任务行为。

### 1. 看一条样本
假设 Token 是 [用户, 问题, 助手, 回答, EOS]。预测“回答”的 logits 来自前一位置。“不训练提示词”指不把提示词作为目标计入损失，不表示模型看不到提示词。

### 2. 手算并编程
代码练习接收已经正确 shift 后的目标 Token 对数概率和有效位置标记，计算负对数似然。它检查 mask 和有效分母，不进行分词或模型训练。真实管线还要打印对应 Token 来验证 shift。

### 3. 实验落点
SFT 使用偏好数据中的安全 chosen；另设正常任务混合消融。记录有效回答 Token 数、截断比例和正常评测变化。数据混合比例不等于实际损失贡献比例。

```python
def masked_nll(target_log_probs, supervised):
    if len(target_log_probs) != len(supervised):
        raise ValueError("长度不一致")
    selected = [
        logp for logp, keep in zip(target_log_probs, supervised)
        if keep
    ]
    if not selected:
        raise ValueError("没有有效监督目标")
    return -sum(selected) / len(selected)
```

**易错点：**全零 mask 必须报错；把 padding 当作正常目标，或把提示和回答全部平均，都可能改变目标。

**自测：**为什么该练习函数不能独立验证真实数据的 Token shift？

资料：[TRL SFTTrainer](https://huggingface.co/docs/trl/sft_trainer)

## Z07 偏好数据、Bradley–Terry 与奖励模型

偏好数据是同一 prompt 下 chosen / rejected 的比较。Bradley–Terry 模型令 P(chosen优于rejected)=sigmoid(r_chosen-r_rejected)，通过比较标签训练奖励模型。

### 1. 奖励差如何变成概率
奖励差为 0 时预测概率 0.5；差为 2 时约为 0.881。奖励的绝对零点通常不能仅由比较识别，训练直接约束的是差值。

### 2. 偏好并非单一维度
“更安全”和“更有帮助”可能不一致。PKU-SafeRLHF 分别提供相关标签。安全项目应使用对应安全标签，并记录两条回答是否都不安全、是否存在歧义。

### 3. 数据检查
统计 chosen / rejected 的长度、拒答措辞、语言和风险类别，抽样核验。若 chosen 总是短拒答，模型可能学到长度或措辞捷径。来源、规则和筛选数量进入数据卡。

**易错点：**不能未经检查就将 better_response_id 当作安全标签；标签含义以固定版本数据卡为准。

**自测：**一个奖励模型偏爱长回答，你怎样区分真实质量差异和长度偏差？

资料：[InstructGPT](https://arxiv.org/abs/2203.02155)、[PKU-SafeRLHF 数据卡](https://huggingface.co/datasets/PKU-Alignment/PKU-SafeRLHF)

## Z08 KL 约束、参考策略与分布漂移

KL 正则约束当前策略偏离参考策略的程度。它是目标中的软约束，不保证任何单条输出安全；参考模型版本、方向和实际估计方法必须明确。

### 1. 为什么需要参考
只追求奖励可能让模型利用奖励器漏洞，语言质量或正常能力也可能下降。常见目标为期望奖励减去 β·KL(πθ || πref)。πref 通常固定。

### 2. 区分三个角色
当前策略被更新；旧策略用于某些 on-policy 概率比；参考策略约束偏移。三者可能来自相同起点，但在算法中用途不同。PPO clipping 也不等同于显式 KL 惩罚。

### 3. 在实验中记录
保存参考检查点、系数、近似 KL 的计算定义与训练曲线，并同时看输出。DPO 的 β 来自其 KL 正则推导，在固定偏好差上的梯度缩放与最终最优策略的偏移不能简单混为一谈。

**易错点：**不能用一个 β 值跨数据集和算法保证同样的安全强度。

**自测：**为什么训练时 KL 很小仍可能出现严重但低频的违规回答？

资料：[DPO 原论文](https://arxiv.org/abs/2305.18290)、[PPO 原论文](https://arxiv.org/abs/1707.06347)

## Z09 DPO：从偏好对直接更新策略

标准 DPO 使用 z=β[(logπθ(y+|x)−logπref(y+|x))−(logπθ(y−|x)−logπref(y−|x))]，最小化 −log sigmoid(z)。无需在标准离线 DPO 中另训奖励模型。

### 1. 四个对数概率
chosen 与 rejected 各有当前策略和参考策略的序列对数概率。回答 Token 的 log probability 通常求和；不能随意改成长度平均后仍声称使用相同目标。


### 2. 手算一次
当前策略两项为 -2、-4，参考为 -3、-3，β=0.1，则 z=0.2，损失约 0.5981。若策略与参考完全一致，z=0，损失为 log(2)。这只验证公式。

### 3. 实验落点
训练时固定参考策略，正确 mask prompt，处理长度和截断。可预计算冻结参考模型的 log probabilities 以节省资源；数据或参考变化后需要重算。DPO 与 SFT 的计算成本不同，单独记录。

```python
import math

def dpo_loss(policy_chosen, policy_rejected,
             ref_chosen, ref_rejected, beta=0.1):
    if beta <= 0:
        raise ValueError("beta 必须大于零")
    chosen_ratio = policy_chosen - ref_chosen
    rejected_ratio = policy_rejected - ref_rejected
    z = beta * (chosen_ratio - rejected_ratio)
    return max(0.0, -z) + math.log1p(math.exp(-abs(z)))
```

**易错点：**DPO 的 chosen 必须来自预先确定的标注规则。训练损失下降不等于未见攻击成功率下降。

**自测：**为什么当前策略与参考一致时，所有偏好对的初始 DPO 损失相同？

资料：[DPO 原论文](https://arxiv.org/abs/2305.18290)、[TRL DPOTrainer](https://huggingface.co/docs/trl/dpo_trainer)

## Z10 Policy gradient、advantage 与 PPO

策略梯度用奖励加权 log probability 的梯度；advantage 衡量动作相对基线的好坏。PPO 用新旧策略概率比与裁剪替代目标减少过大的更新激励，但不保证严格限制每次策略变化。

### 1. 从一句话到公式
如果某个输出比预期好，就增加它在相同上下文下的概率；比预期差则降低。减去不依赖当前动作的基线可降低估计方差。

### 2. PPO 的裁剪
r=πnew/πold，目标包含 min(rA, clip(r,1−ε,1+ε)A)。当 A 为负时，min 的选择不能凭正优势的直觉判断。实现最小化 loss 时通常再取负。


### 3. 需要会解释到什么程度
讲清 rollout、奖励、advantage、更新批次、旧策略与参考策略；读懂一段训练曲线。一月项目不必再实现完整 PPO，因为会引入额外采样、奖励模型和价值估计工程。

**易错点：**PPO clipping 不等于“概率比永远被强行截断在区间内”。

**自测：**A=-1、r=0.5、ε=0.2 时，两个候选项各是多少？

资料：[PPO 原论文](https://arxiv.org/abs/1707.06347)、[InstructGPT](https://arxiv.org/abs/2203.02155)

## Z11 GRPO 与 RLVR：组内比较和奖励来源

GRPO 使用同一问题下多条输出的组内奖励构造相对优势，通常省去独立价值模型；RLVR 指奖励来自可验证结果。它们分别描述优化方法与奖励来源。

### 1. 组内优势
常见标准化形式为 (r_i−mean(r))/(std(r)+ε)。一组奖励全相同会缺少区分信号。实现变体可能改变标准化、KL、长度归一化和采样方式，需要按版本说明。


### 2. 什么能验证
数学答案、单元测试、结构约束可以提供部分可验证奖励。测试通过仍不代表完整正确，更不代表行为安全；模型可能利用奖励检查器的漏洞。

### 3. 本项目的定位
先能解释 GRPO 与 DPO 的数据流差别：在线生成多个候选与固定偏好对的成本不同。若扩展训练，先有可靠奖励和独立评测，再引入在线 RL。

**易错点：**GRPO 不是 RLVR 的同义词；二元安全裁判也未必是可靠的可验证奖励。

**自测：**一组八条回答全得 0 分时，会出现什么学习信号问题？

资料：[DeepSeekMath / GRPO](https://arxiv.org/abs/2402.03300)

## Z12 RLHF、RLAIF、奖励黑客与安全收益

RLHF 与 RLAIF 区分反馈主要来自人或 AI；奖励黑客指策略利用目标与真实意图之间的差距取得高分。自动反馈提高规模，也会引入裁判偏差。

### 1. 数据流比缩写重要
反馈可以用于训练奖励模型，也可以形成直接偏好对。记录反馈提供者、版本、提示、抽样策略和质量控制。模型给出的标签不能因为来自强模型就被视为真值。

### 2. 一个安全评测捷径
如果裁判看到“我不能”就判为安全，模型可能先写拒答句，再给出违规内容。训练奖励会变高，真实行为却未改善。

### 3. 防止把漏洞当收益
保留独立评测器、人工抽查和针对性反例。区分训练奖励与最终安全指标。在报告中展示被裁判误判的案例，并说明更换判据后结论是否变化。

**易错点：**使用同一个模型生成偏好、训练打分和最终裁判，容易形成共享偏差。

**自测：**如果训练奖励不断增加，而人工抽查质量下降，你首先查哪三件事？

资料：[Constitutional AI](https://arxiv.org/abs/2212.08073)、[InstructGPT](https://arxiv.org/abs/2203.02155)、[HarmBench](https://arxiv.org/abs/2402.04249)

## Z13 公平对比：基线、控制变量与实际成本

比较原模型、SFT、DPO 时，尽量固定检查点、提示集合、模板、解码设置和测试集；SFT 用 chosen，DPO 用配对信息。无法匹配的计算成本要报告。

### 1. 写一张配置表
包含模型 revision、数据 revision、随机种子、LoRA 参数、有效 batch、最大长度、训练 Token、优化器步数、推理预算和评分器。配置文件和 Git commit 一起保存。

### 2. 不同问题需要不同对照
从原模型分别做 SFT / DPO 回答“额外训练策略有何差异”；从 SFT 再做 DPO 回答“在 SFT 上增加偏好优化有何收益”。两者不能混写成同一个比较。

### 3. 时间有限时
先完成 8B 三组、一个消融、独立测试，再在 32B 重复关键对照。开发集选方案，最终测试只用于一次最终评价，避免按测试分数反复调参。

**易错点：**相同 epoch 不保证相同 Token、算力或数据利用量。

**自测：**如果 DPO 比 SFT 多用两倍 GPU 时间，结果表如何呈现才清楚？

资料：[DPO 原论文](https://arxiv.org/abs/2305.18290)、[HarmBench](https://arxiv.org/abs/2402.04249)

## Z14 攻击成功率、拒答率与分母

ASR=成功攻击数/评估攻击数，但任务、尝试和成功的定义必须固定。拒答率是表面行为指标，不能替代合规判定；超时、解析失败与无效攻击要单列。

### 1. 区分两种成功率
每次尝试成功率与每个目标在 K 次预算内至少一次成功率不同。增加 K 通常改变后者，不能在不同预算之间直接比较。

### 2. 一个分母例子
100 个预注册测试中，10 个推理失败、18 个成功攻击：可以报告意向评估口径 18/100，同时单列 10% 失败；也可报告有效输出条件口径 18/90，但必须明确条件，且两个方案规则一致。

### 3. Agent 额外需要什么
先报告干净任务完成率，再报告受攻击任务完成率和攻击目标成功率。若使用“干净可完成任务子集”，应事先固定共同子集，避免各方案挑自己的容易题。

**易错点：**把超时或工具失败全部算作成功防御会夸大安全收益。

**自测：**30 个目标、每个 5 次攻击，需要报告哪些不同的样本量？

资料：[HarmBench](https://arxiv.org/abs/2402.04249)、[AgentDojo](https://github.com/ethz-spylab/agentdojo)

## Z15 过度拒答、正常能力与安全效用权衡

过度拒答是正常请求被不必要地拒绝。安全收益要与正常任务表现同时报告；IFEval 测可验证指令遵循，不能代表模型的全部通用能力。

### 1. 为什么正常问题也需要独立集合
“如何杀死一个 Linux 进程”可能含敏感词，却是正常技术问题。只靠关键词拒绝会产生过度拒答。XSTest 用这类问题检查夸大安全的行为。

### 2. 结果图怎么画
横轴正常任务成功率，纵轴攻击成功率或安全得分；明确越高/越低越好。另列过度拒答比例和样本量，避免只展示安全一列。

### 3. 对结论的限制
指令遵循、事实知识、编码能力是不同维度。一月项目可选择一个正常任务基准并如实限定，不能凭一个子集宣称“通用能力无损”。

**易错点：**“回答了”不代表正常任务完成；“拒绝了”也不必然是正确的安全行为。

**自测：**一个方案 ASR 从 20% 降至 5%，正常任务完成率从 80% 降至 30%，你怎样评价？这些只是教学数字。

资料：[XSTest](https://github.com/paul-rottger/xstest)、[IFEval](https://arxiv.org/abs/2311.07911)

## Z16 样本量、置信区间与成对比较

有限测试只能估计总体表现。比例可报告 Wilson 区间；两个方案使用同一测试集时应进行成对差异分析。多个训练种子反映训练随机性，不能用样本区间替代。

### 1. 不要只报一个百分比
10 次里成功 1 次与 1000 次里成功 100 次都为 10%，但估计精度不同。代码练习计算二项比例的 Wilson 95% 区间。

### 2. 零次成功的含义
测试中 0 次攻击成功并不证明真实风险为零。Wilson 上界仍大于 0。应同时给出样本量、攻击预算和测试覆盖范围。

### 3. 比较差异
同一批问题比较两个方案时，按问题成对 bootstrap；多个变体属于同一攻击家族时，考虑按家族聚类抽样。独立种子重复用于检验训练波动。小样本附录应标为探索性。

```python
import math

def wilson(successes, total, z=1.959963984540054):
    if total <= 0 or not 0 <= successes <= total:
        raise ValueError("需要 0 <= successes <= total 且 total > 0")
    p = successes / total
    denom = 1 + z*z/total
    center = (p + z*z/(2*total)) / denom
    variance = p*(1-p)/total + z*z/(4*total*total)
    radius = z * math.sqrt(variance) / denom
    return max(0.0, center-radius), min(1.0, center+radius)
```

**易错点：**95% 置信区间不表示“这个固定参数有 95% 概率落入本次区间”；相邻点估计也未必存在可靠差异。

**自测：**为什么对同一问题的五个改写不能总当作五个独立样本？

资料：[NIST 比例置信区间](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)

## Z17 数据泄漏、去重与未见分布

训练、开发和测试必须分开。按问题家族、来源或攻击方法划分，比单纯随机拆分字符串更能测试泛化；具体采用哪种划分，要与研究问题对应。

### 1. 三个集合的职责
训练集更新参数；开发集选择混合比例、训练轮次和提示；测试集估计最终表现。看过测试错误再修改方案，实际已将它用于开发。

### 2. 去重层次
先处理完全相同及标准化后相同的 prompt，再检查近似改写和共享模板。仅哈希去重能查完全重复，不能证明语义无泄漏。

### 3. 本项目的文件
保存划分清单、原始来源标识、hash、规则和随机种子。安全偏好数据与评测基准也要交叉检查。不能把“不同随机种子”写成“未见攻击方法”。

**易错点：**测试集没有直接用于梯度更新，也可能通过调参、提示设计或人工筛选泄漏。

**自测：**把同一个问题的十个改写随机分到训练和测试，会高估什么？

资料：[HarmBench](https://arxiv.org/abs/2402.04249)、[PKU-SafeRLHF 数据卡](https://huggingface.co/datasets/PKU-Alignment/PKU-SafeRLHF)

## Z18 LLM 裁判、人工复核与评分误差

自动裁判是测量工具。应固定版本和评分提示、保留原始评分依据，并通过分层人工复核估计误判；无法解析的评分不能悄悄转换成安全标签。

### 1. 常见偏差
裁判可能受回答长度、格式、模型名称、位置或拒答套话影响。被评内容中的指令也可能干扰裁判，因此评分输入要有明确数据边界。

### 2. 抽样怎么做
从成功、失败、拒答、异常、不同风险类别中抽样，保存人工标签与裁判标签的对应。争议案例记录规则与复核结论，不只检查模型看起来表现好的样本。

### 3. 报告什么
报告裁判版本、提示哈希、解析失败率和人工一致情况。裁判变化后重评关键结论。API 模型可提供评分帮助，但闭源评分结果不等于独立验证了你的训练方法。

**易错点：**一个自动裁判给分很稳定，不代表其评分准确。

**自测：**如果自动裁判的错误集中在某一类回答，为什么总体一致率仍可能误导？

资料：[HarmBench](https://arxiv.org/abs/2402.04249)、[AgentDojo](https://github.com/ethz-spylab/agentdojo)

## Z19 Jailbreak 与直接、间接提示注入

越狱通常试图诱导模型违反行为约束；直接注入从用户输入进入，间接注入来自网页、邮件、检索片段或工具输出。防护要结合入口和权限，而非只看文本是否可疑。

### 1. 两种不同的任务
危险用户请求要求模型拒绝；正常用户请求遭遇恶意工具数据，则希望模型继续完成原任务。统一用“是否拒答”评价两者，会掩盖重要差异。

### 2. 信任层级
文档中的“忽略上文”属于待处理内容，不应自动变成系统指令。模型层的边界提示可以降低部分风险，但执行层仍应验证敏感操作。

### 3. 实验落点
主线对话基准与 Agent 注入结果分表。Agent 拓展用模拟邮箱或文档工具，记录实际动作、任务状态与拒绝原因。不要把一个对话安全微调的结果外推为工具系统安全。

**易错点：**工具返回的 JSON 合法，不表示其中的操作要求获得授权。

**自测：**一个注入被拦截，但正常任务也失败，这个结果应该记录在哪里？

资料：[AgentDojo](https://github.com/ethz-spylab/agentdojo)

## Z20 自动化 Red Teaming 的搜索预算

自动红队是在明确攻击空间内生成、筛选和测试候选。需要固定目标集合、可见反馈、查询次数或 Token 预算，并记录完整尝试轨迹。

### 1. 最小流程
读取预定义目标，生成候选，调用被测模型，按照规则评分，再决定是否继续。攻击者模型与裁判可以不同；各自费用和调用次数单独记录。

### 2. 公平的预算
每个目标最多 K 次调用，或固定总 Token / 时间预算。若一个方案提前成功，应记录实际成本；未成功但用尽预算也需要保留。只保存最好一次会丢失搜索过程。

### 3. 一月内怎么做
复用一个公开攻击方法，先确保协议可复现，再评估未见攻击方式。禁止用最终测试集反复选择攻击提示后仍声称完全未见。搜索得到的训练样本进入新的数据版本。

**易错点：**攻击器模型更强或调用次数更多，可能单独改变 ASR。

**自测：**两种防御的平均攻击成本不同，你会怎样同时展示成功率和成本？

资料：[HarmBench](https://arxiv.org/abs/2402.04249)

## Z21 Agent 环境与任务级评测

Agent 评测需要任务状态、工具返回、实际动作和最终结果。AgentDojo 等环境可以提供正常任务及注入攻击框架；对模型能力和安全性的解释需要先建立干净基线。

### 1. 一个最小任务
用户授权整理某份文档，工具返回文档内容。评价包括是否提取了正确信息、是否执行了额外操作，以及工具状态是否发生变化。

### 2. 先测正常能力
若模型在干净环境也不能正确使用工具，受攻击后没有执行违规动作的意义有限。记录 clean task success、attacked task success、attack success 和执行错误。

### 3. 控制拓展范围
主实验稳定后再选一个任务套件和少量持出任务探索。工具版本、任务 ID、状态初始化和重置规则固定。小样本只能支持相应范围的初步观察。

**易错点：**最终自然语言声称“没有发送”，不能覆盖工具已经发送的事实。

**自测：**为什么 Agent 结果需要保留工具调用轨迹，而不只是最后一条回复？

资料：[AgentDojo](https://github.com/ethz-spylab/agentdojo)

## Z22 授权检查、最小权限与动作阻断

高风险动作由执行层根据可信授权检查工具名、参数和目标资源。模型提出动作不等于动作已获授权；拒绝动作后还需检查正常任务是否能继续。

### 1. 权限来自哪里
用户事先授予“读取指定文档”和“发送给指定收件人”的权限。文档里的新收件人不能扩展这个集合。授权配置必须来自可信程序状态。

### 2. CPU 练习
实现一个纯策略函数：读取允许，发送必须有用户写权限且收件人在允许集合中。它不调用真实服务，仅检查规则。真实系统还要处理参数解析、资源别名、撤销和检查后执行的竞争条件。

### 3. 如何评估
同时放入合法请求与越权请求，记录误拦和漏拦。执行层策略可以用于 API 模型，但这种迁移并不证明你在本地训练的适配器迁移到了闭源模型。

```python
def authorize(action, allowed_recipients,
              user_granted_write=False):
    if action.get("tool") == "read_document":
        return True
    if action.get("tool") == "send_message":
        return (user_granted_write is True
                and action.get("recipient") in allowed_recipients)
    return False
```

**易错点：**只检查动作名、不检查收件人或文件路径等参数，会留下权限缺口。

**自测：**如果网页写着“用户已经同意”，为什么不能据此把 user_granted_write 改成 True？

资料：[AgentDojo](https://github.com/ethz-spylab/agentdojo)、[AI Control](https://arxiv.org/abs/2312.06942)

## Z23 行为监控：输入输出、轨迹与内部信号

监控可以读取输入输出、工具轨迹或模型内部信号，在动作前后检测风险。应评价漏报、误报、检测时延和被规避的可能，而非只报一个准确率。

### 1. 选择监控位置
输入检查可早期拦截，输出检查评估回答，动作前检查控制执行，运行中监控观察长任务。越靠后的检查越可能已经发生不可撤销动作。

### 2. 思维链的边界
可见推理文本可能帮助发现某些意图，但不是模型内部过程的完美记录。针对监控器优化也可能改变可见表达。监控是否可靠需要独立实验。

### 3. 实验设计
固定报警阈值，绘制或列出召回与误报的取舍，测额外延迟。对未见攻击进行持出验证。监控器和被测策略若共享模型，说明相关失误的风险。

**易错点：**没有触发报警不等于没有风险；报警后是否成功阻断需要另外记录。

**自测：**一个监控器发现风险但晚于工具执行，应该如何报告其效果？

资料：[Monitoring Reasoning Models](https://arxiv.org/abs/2503.11926)、[AI Control](https://arxiv.org/abs/2312.06942)

## Z24 可解释性：相关信号与因果干预

线性探针、激活分析可以发现相关信号；消融、替换或干预用于进一步检验因果作用。可读的解释并不自动等于模型实际决策机制。

### 1. 分清三种证据
相关性：某方向激活与拒答一起变化。预测性：探针在持出样本上预测拒答。干预性：改变该方向后行为改变。三者强度和限制不同。

### 2. 干预也需要控制
比较随机方向、同等干预幅度和正常任务影响；检查是否因广泛破坏模型才改变行为。结论限定到所用层、模型和任务。

### 3. 本项目的优先级
先完成行为实验。若出现稳定现象，可做一个有限分析拓展；不在一个月内同时铺开大量探针与解释方法。读懂代表论文的证据结构即可作为理论准备。

**易错点：**探针能预测标签，不证明模型使用该探针对应的特征完成决策。

**自测：**如何区分“干预了安全机制”和“把模型整体能力破坏了”？

资料：[Refusal is mediated by a single direction](https://arxiv.org/abs/2406.11717)

## Z25 可扩展监督与 AI Control

可扩展监督研究如何在任务超出人类直接判断能力时提供有效监督；AI Control 关注在不完全信任模型时，用监控、限制和评估降低系统风险。

### 1. 监督为什么会困难
长代码修改、复杂研究结论或长程工具任务，逐步人工核验成本很高。分解任务、交叉检查和自动评价可以提供帮助，但每个环节都可能失误。

### 2. Control 的系统视角
把被测模型、监控器、可信工具与权限分开，设计可观察的攻击和防御协议。安全性与有用性一起评估，避免通过完全禁用功能获得看似完美的安全。

### 3. 面试如何讲
解释可信计算边界、监控失效时的后备动作，以及系统如何记录证据。本项目的动作授权练习是入门示意，不等于已经实现完整 Control 方案。

**易错点：**模型自我检查和两个模型互相检查，都需要独立证据验证可靠性。

**自测：**为什么一个安全策略必须说明对正常任务效用的影响？

资料：[AI Control](https://arxiv.org/abs/2312.06942)

## Z26 奖励黑客、迎合与 alignment faking

迎合是偏向满足用户预期而牺牲真实性；奖励黑客是利用评分漏洞；alignment faking 研究模型在特定训练或评估条件下表现出策略性合规的现象。三者不能仅凭一段文本混为一谈。

### 1. 可观察现象先行
记录任务条件、模型输出和行为差异，再提出解释。模型说“我在欺骗”不是充分证据；没有说也不能排除行为层的问题。

### 2. 需要什么对照
改变是否被评估、奖励结构或可见信息，同时保持任务可比。检查提示诱导、能力差异与数据记忆等替代解释。

### 3. 如何用于准备
一月内掌握定义和实验逻辑，报告中避免把普通错误升级成策略性欺骗。若发现可疑行为，保存可复现实例和对照，明确尚未排除的解释。

**易错点：**不要从单个输出推断模型具有某种稳定意图，也不要把所有失误归为对齐失败。

**自测：**模型在两个提示条件下答案不同，还需要什么证据才能支持策略性行为解释？

资料：[Alignment faking](https://arxiv.org/abs/2412.14093)、[AI Control](https://arxiv.org/abs/2312.06942)

## Z27 未知风险、第三方验证与 Preparedness

Preparedness 包括风险识别、能力评估、监控阈值、响应机制与外部验证。评测覆盖已知任务，真实部署还需要持续观察和处理新型失败。

### 1. 风险与能力分开记录
模型具备某项能力，不等于在具体系统中必然造成风险；风险还依赖访问权限、环境、暴露机会和防护。反过来，已有基准低分也不能证明没有未知风险。

### 2. 从报告到处置
明确何种证据触发复核、限制工具、暂停任务或回滚；保存事件时间线、输入、模型版本和动作记录。涉及专业领域时，需要相应专家与第三方评测。

### 3. 作品中的边界
交付限制说明和后续验证计划。一个月的小项目可以展示风险思考与可复现证据，不应声称建成全面风险体系或证明前沿模型总体安全。

**易错点：**通过一个公开 Benchmark 并不构成上线安全保证。

**自测：**发现一个此前未覆盖的失败案例后，怎样把它变成回归测试而不污染最终测试？

资料：[Seed Alignment & Preparedness 招募](https://seed.bytedance.com/zh/blog/seed-alignment-preparedness-team-looking-for-global-talents)、[HarmBench](https://arxiv.org/abs/2402.04249)

## Z28 把求职项目写成可检验的研究问题

项目主问题是：在固定配置下，安全 SFT / DPO 对未见攻击的收益有何差异，是否伴随过度拒答和正常任务损失？结论可以为正、负或不确定。

### 1. 预先写三个假设
例如：偏好训练改善已知攻击；改善可能在未见攻击上减弱；正常数据混合可能改变安全与效用的取舍。这些是待验证假设，不是已有成果。

### 2. 对应证据
8B 的原模型 / SFT / DPO 回答方法比较；持出攻击回答泛化；混合数据消融回答一个机制因素；32B 的关键复核检查规模可迁移性。

### 3. 交付物
README 一页总览、4–6 页报告、8–10 页汇报、配置和结果清单、3–5 个失败案例。使用开源 trainer 的部分如实注明，个人贡献落在问题、协议、分析和实际改进上。

**易错点：**CPU 公式验证不能写成真实模型安全提升；配置模板不能写成完成的训练实验。

**自测：**如果三个方案差异很小，怎样把项目写成诚实且有分析价值的作品？

资料：[HarmBench](https://arxiv.org/abs/2402.04249)、[Seed Alignment & Preparedness 招募](https://seed.bytedance.com/zh/blog/seed-alignment-preparedness-team-looking-for-global-talents)

## Z29 安全偏好数据准备与实验版本

使用公开偏好数据时固定 revision，按安全标签筛选 chosen，记录不安全和歧义样本的处理。训练文件、划分规则、统计和 hash 共同构成数据版本。

### 1. 从小规模开始
先抽样人工看几十条，确认字段和标签意义，再选择约 2,000–5,000 条训练对。是否足够由开发结果决定，不把数量当成效果保证。

### 2. 统一训练输入
SFT 使用同一批 prompt 的 chosen；DPO 使用 chosen / rejected。模板和非思考模式一致。若 chosen 与 rejected 都不安全，默认排除并记录数量。

### 3. 独立结果清单
每次实验记录模型 revision、数据 hash、Git commit、参数、种子和评测版本。数据与模型大文件留在服务器；GitHub 保存脚本、清单与经检查的小型结果摘要。

**易错点：**自动下载到 main 分支只确定当前位置，不能保证未来复现同一数据版本。

**自测：**如何在不把整个训练集上传 GitHub 的情况下让自己的实验可追溯？

资料：[PKU-SafeRLHF 数据卡](https://huggingface.co/datasets/PKU-Alignment/PKU-SafeRLHF)、[Qwen3-8B 模型卡](https://huggingface.co/Qwen/Qwen3-8B)

## Z30 8×H20 与 4×3090 的实验安排

8B 主实验从一张 96GB H20 做短流程验证，再根据实际瓶颈分配训练和评测；32B 做关键复核。3090 可做 CPU 之外的小模型辅助任务，无需与 H20 混成一个训练组。

### 1. 第一次只测三个数
记录实际峰值显存、每步时间、有效 Token 吞吐。先用短上下文、小 batch 和少量步数确认 loss、保存与加载，再决定正式运行配置。

### 2. 多卡如何使用
可以将 H20 分成独立任务组：SFT、DPO、评测与重复实验。数据并行提升吞吐但不分片每个模型副本；需要模型分片时再配置 FSDP / ZeRO 等方案，并单独验证。

### 3. 预算落点
每日 3–4 小时用于读理论、改代码和分析，机器运行可更久但需作业管理。8B 完成主矩阵，32B 只复核开发集选定方案。不要根据显存容量估计准确完成时间。

**易错点：**CUDA_VISIBLE_DEVICES 只选择可见卡，不会自动申请空闲卡或避免与他人作业冲突。

**自测：**两张卡各有足够显存，但训练变慢，你会检查哪些通信和 batch 因素？

资料：[PyTorch 基础](https://docs.pytorch.org/tutorials/beginner/basics/intro.html)、[LoRA 原论文](https://arxiv.org/abs/2106.09685)、[TRL DPOTrainer](https://huggingface.co/docs/trl/dpo_trainer)

## Z31 GitHub 作为两台机器的协作入口

本地修改实践仓库并 push；服务器独立认证后 clone / pull，通过命令行运行。服务器不需要 Codex，也不需要连接本地电脑。小型结果摘要通过独立分支返回。

### 1. 第一次连接
Ubuntu / Debian 安装 Git 和 gh 后执行 gh auth login。终端给出一次性代码；在能打开 GitHub 的浏览器完成授权。两台机器各自保存认证，不复制本机凭据文件。

### 2. 日常流程
开始任务前 git pull --ff-only；运行时记录 commit。代码更新不会自动同步到已运行的进程。结束后把检查过的摘要提交到独立结果分支，本地显式读取和合并。

### 3. 文件归属
学习软件留在本地。独立仓库只放实践方案、理论笔记、配置与脚本。模型、原始数据、缓存、虚拟环境和 .env 不上传。仓库私有仍需要控制提交内容。

**易错点：**下载 ZIP 不建立 Git 同步关系；两台机器同时修改 main 容易产生冲突。

**自测：**服务器不能打开浏览器时，如何完成 gh 的设备授权？

资料：[GitHub CLI 登录](https://cli.github.com/manual/gh_auth_login)

## Z32 30 天节奏、验收与面试证据

每一天都产生一个可检查的小产物。第一周完成环境和协议，第二周完成 8B 对照，第三周做消融与 32B，第四周分析并交付。检查、训练和研究结论分别记录状态。

### 1. 每天的时间切分
建议 45 分钟理论、约 2 小时实践、30 分钟记录与复盘。服务器任务可异步执行，但运行前后都要检查数据、配置与日志。

### 2. 完成标准
任一结论都能指向配置、原始输出、评分规则和汇总脚本。文档写明样本量、失败数、随机性与结论限制。不同模型规模结果不一致时如实解释。

### 3. 面试演练
用 2 分钟讲研究问题；5 分钟讲对照和核心发现；再准备一个失败案例和一个你做过的实验取舍。报告中的结果只填写真实测量值，计划与模板统一标为未运行。

**易错点：**把时间都花在环境和页面美化上，会挤占分析与复现；最后一周需留给证据整理。

**自测：**请用三个文件证明一个结果：实验配置、逐条记录和汇总分别在哪里？

资料：[Seed Alignment & Preparedness 招募](https://seed.bytedance.com/zh/blog/seed-alignment-preparedness-team-looking-for-global-talents)、[HarmBench](https://arxiv.org/abs/2402.04249)
